# Quant Lab 2.8 isolated offline groundwork

This is offline preparation only. It does not deploy a task or authorize any network request, research, trading, recovery or old-instance changes. Keep the old instance, its 7/28-day start, failure evidence and interrupted run intact.

In a separately approved isolated test directory, create a source-block record outside every instance, then use `deployment.archive_instance initialize-empty` with a distinct absolute root, that gate, a distinct `quant-lab-archive-*` task name and a completed UTC start date. Initialization creates an instance ID, empty collection ledger, baseline snapshot and separate metadata; it does not record a first observation or task enable time. It refuses partial initialization or differing evidence. A source-block record has only one supported state: blocked. There is deliberately no allow or recovery command.

The service checks the source record, the instance identity and the baseline binding. New-instance source access remains unconditionally blocked, including after restarts, fresh budgets and reinstallation. A source record which is missing or changed fails closed. Test-only mocks of this check do not demonstrate production access. `archive-service.ps1 -Action Plan -TaskName ...` produces a plan; registration of a new instance task is disabled. The old default task name and legacy data semantics remain available.

An event export can identify a task name and a Task Scheduler trigger event. For a new instance the acceptance report requires a deployment identity, matching event record and hash, and uses that trigger as a **conservative observation start**, not proof of the exact enable time, complete scheduler history or collection success. There is currently no supported production activation workflow. Never manufacture deployment records or treat a trigger as a successful collection. First-time retrieval of an older archive is labelled retrospective; it is not a prospective research sample. Formal admission remains insufficient_evidence.

## Security boundary and remaining work

The source block applies to instances created and run through this version's managed service; it is not an operating-system security boundary. Older code, standalone unregistered directories, arbitrary local code, administrators or direct API calls can still reach the source without consulting it. Per-instance locks do not serialize different roots. Before production use a separately reviewed mechanism must establish exclusive source-wide writer control, old task/process/handle isolation, and source and network review immediately before each request, and must fail closed when those facts are unknown or change. Do not release the block to work around old failures or TLS/access restrictions. Same-disk hash chains cannot detect coherent rollback. Request admission is intentionally unavailable until these conditions are verifiable.

2.8 snapshots preserve exact 2.6/2.7 historical semantics and accept only explicitly pinned observer hashes; unknown fingerprints remain rejected. Independent 7/28-day windows cannot merge old and new observations. Production task creation, ACL changes, network diagnostics, real collection and all related authorization remain out of scope.
